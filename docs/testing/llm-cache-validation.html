Testing cost optimizations in LLM pipelines

Use deterministic tests to prove which work is avoided, integration tests to prove the shipped package behaves correctly, and bounded model evaluations to assess the costs and quality that local substitutes cannot measure.

Start with the work the system repeats

A multi-stage language-model pipeline often extracts observations from separate chunks of source material, merges large results, drafts an answer, reviews it against evidence, and translates the accepted text. A failure near the end can cause an expensive restart even when earlier stages succeeded.

Consider a local CLI that turns a person's prompt history into an evidence-backed report. In prompt-profile, chunk analysis is called map; merge compresses observations when needed; draft writes the profile; review checks it against the original analysis context; and translation produces another language. The CLI normally uses the user's logged-in Claude Code or Codex executable.

Stage checkpoints save successful intermediate results so a retry can continue without repeating every model call. They fit a system where retries or repeated inputs occur, saved results are acceptable to reuse, and the inputs that determine a result can be identified. If every invocation must produce a fresh independent answer, reuse changes the product's meaning.

The simplest implementation caches the whole final report. That can help identical completed runs, but cannot recover a successful draft after review fails. Caching each successful stage addresses that failure boundary. It also creates new obligations: correct invalidation, validated stored output, accurate provenance, private storage, and fresh execution accounting.

Separate three claims before choosing tests

“The optimization works” can mean three different things. Each needs a different kind of evidence.

Claims and the evidence that can support them
Claim Suitable evidence What remains unknown
Less repeated work Actual stage-call records under fixed input, injected failures, and cache hits. Avoided calls do not directly reveal token prices or subscription deductions.
Lower provider consumption Real CLI measurements with token categories, failed attempts, model/configuration provenance, and cost coverage. API list-price equivalents do not establish subscription-quota deductions.
Acceptable output quality Source-grounded review of claims, omissions, counterexamples, and translation fidelity on representative cases. Schema validity, exact quotations, and model agreement do not establish semantic support.

A deterministic model substitute makes control flow observable: for the same input it returns a predictable JSON response. This removes model randomness from a cache test. It can establish that the program avoids a call or rejects invalid structure; it cannot establish that a real model would reach the same interpretation.

Test reuse and invalidation together

A useful test suite checks both sides of the cache contract: unchanged dependencies reuse an accepted result, while changed dependencies cause the affected stage to run again. A test that only checks warm-cache savings can pass even when the cache is dangerously broad.

Mechanisms matched to their failure modes
Mechanism Failure it addresses Behavior to test
Stage input identity Reusing output for different source material or instructions. Changing the prompt, system instructions, model, or effort causes a miss.
Stage-specific dependencies A translation edit unnecessarily evicts source observations. Changing translation instructions preserves map keys; changing reduce instructions invalidates draft and review keys.
Successful checkpoints A late failure repeats completed work. Inject a failure at review or translation, retain cache, then restart with a new runner.
Validation on read Damaged or incompatible cached JSON bypasses normal checks. Malformed files and wrong field types become misses; cached content still passes evidence or language checks.
Fresh accounting Historical usage appears as new consumption. A cache hit adds no model attempt, old tokens, old cost, or old call duration; the new report receives a fresh execution identity.

The current implementation hashes stage prompts and schemas independently and retains explicit stage revisions for code changes that those hashes cannot capture. Review depends on both drafting and review instructions. Tests simulate prompt edits through the prompt loader and compare the resulting cache keys. This tests dependency behavior, not the wording quality of the new prompt.

Generated checkpoints are decoded against the requesting schema. Translation checkpoints also pass shape alignment and language checks. Tests corrupt stored values, exercise incomplete translations followed by valid replacements, and verify that --no-cache skips reads while still refreshing successful checkpoints.

One subtle invalidation source is a changing query clock. If the source history has not changed but the request contains a new “until now” timestamp, a full-input hash will miss on every restart. The report pipeline omits that selection window from the statistics sent to the model, retains the observed data date range and measured statistics, and saves the full selection window in the newly assembled report. A regression test advances only the window and checks both reuse and fresh report metadata. This choice needs separate quality evaluation if the model's interpretation depends on the requested period rather than the observed records.

A controlled comparison with a late-stage failure

A local probe ran the same fictional workload against baseline commit 2c5feaa and an isolated snapshot containing the checkpoint changes. Both used Node 24.18.0, the same deterministic runner, 80 fictional prompts across 40 days, fixed requested model and effort, and English plus Traditional Chinese output. The selected prompts formed twelve map chunks; this probe did not exercise the merge path.

The first run required twelve map calls, one draft, one review, and one translation. After a successful run, a second runner reused the same cache. For review recovery, the probe first allowed the draft to succeed and injected a ProcessFailed error at review. For translation recovery, it injected failures for both bounded translation attempts, retained the successful English stages, and restarted.

The full nine-scenario probe also covered advancing the selection clock, bypassing cache, changing model, changing effort, and changing narration voice. Voice changes regenerated draft, review, and translation while reusing observations. Model and effort changes regenerated all stages. These are desired misses: minimizing calls alone would reward an incorrect cache.

Scope of the comparison. The fixture reused simplified empty-data statistics alongside the 80 prompts. It did not represent complete production statistics. The runner returned deterministic prose and did not evaluate narration changes. It did not use the production retry wrapper, measure provider tokens, establish realistic latency, or access real user history. The baseline and candidate snapshots also differed in unrelated report code, which this analysis-only probe did not render.

The probe compared hashes of core content fields, excluding execution metadata that should change. It also checked that a planted nonexistent quotation did not survive into published content. Equal hashes show preservation under this controlled response function. They are not evidence that real models produce equivalent claims, nor proof that every unsupported citation can be detected. The committed result snapshot records all nine cases and their scope.

Cross the boundaries that a unit test replaces

The controlled comparison used in-memory caches and a fake runner. Disk serialization, process spawning, packaging, and asset resolution can still fail even if that comparison passes. Each additional layer should exercise one of those boundaries.

File-cache tests write checkpoints to temporary directories, read them back, corrupt JSON, check new directory and file permissions, and verify clearing stage folders preserves fonts. The CLI accounting tests compare the terminal summary, saved execution record, and report generation metadata. A warm run must create a new execution while recording no new model attempts or historical consumption.

The installed-package check builds a tarball, installs it outside the checkout, and exercises version/help, prompt and font assets, dry-run behavior, and offline HTML, JSON, and PNG rendering. This alone does not exercise generated-stage checkpoints, so a second integration probe installs a fake claude executable on a restricted PATH. That executable reports a synthetic login and returns fixed JSON through the real process runner.

With that installed package, a cold English-only run invoked two maps, draft, and review. Its warm rerun added no fake generation invocations, recorded four local cache hits, used a fresh execution ID, and retained private generated checkpoint files. Synthetic usage fields are not provider receipts; the useful observation is the absence of additional process invocations.

Repository-wide type, lint, formatting, and unit checks add regression coverage. The recorded validation passed 113 test files and 1,013 tests under Node 26.13.0; those are whole-suite totals, not newly authored cache tests. The isolated comparison and installed fake-provider probe used Node 24.18.0 on the same macOS machine. This is not a cross-platform validation claim.

When this is a good default

For a resumable pipeline with expensive stages and reusable intermediate results, layered deterministic tests are a strong default. They provide fast, repeatable evidence about call admission, checkpoint boundaries, and invalidation before spending model quota. They optimize diagnosis and regression prevention while accepting the maintenance cost of fixtures and substitutes.

The credible simpler alternative is a few end-to-end runs against a real model. That is valuable for provider compatibility and output quality, but randomness and external failures make it harder to isolate a cache bug. Repeated paid runs are also a costly way to test a malformed cache file. Conversely, an elaborate stage-checkpoint system is excessive for a one-shot transformation with negligible cost and no retry requirement.

Do not use a deterministic substitute as the sole acceptance test when the optimization changes model choice, reasoning effort, evidence selection, review instructions, or translation behavior. These changes can reduce calls while weakening the answer. They require a representative quality evaluation even when every local test passes.

Checkpoint design also has limits. A requested default model is not a stable provider-model identity. Persistent results need a privacy and cleanup policy. A timeout does not prove that a provider consumed nothing. A checkpoint write can fail after the model already did the work. Tests should expose these states rather than silently classify them as free or successful.

Choose the next evidence by the remaining uncertainty

If the remaining question is whether unchanged inputs trigger avoidable work, inspect stage records with a deterministic runner. If it is whether an installed CLI can load assets and persist results, test the installed package across that boundary. If it is whether the new design preserves useful claims or lowers provider consumption, use a bounded real-model evaluation.

For that evaluation, freeze representative, authorized source material and selection rules; record model, effort, versions, every attempt, token categories, and measurement coverage. Evaluate cold runs, warm runs, and failure recovery separately. Count failed attempts in total consumption. Review claim support, omissions, counterexamples, and translation fidelity against the source, with missing context marked unknown. Predeclare a call budget and success criteria; no real-model evaluation is implied by a passing offline suite.

Before adopting the pattern, ask whether intermediate results are safe to reuse, whether their dependencies can be identified, and which remaining uncertainty requires a real-model evaluation. When those conditions hold, stage checkpoints and layered tests are a defensible default. When freshness or semantic change dominates, spend the validation budget at that boundary instead.

Implementation and evidence

  • Execution accounting and recovery: operational behavior, measurement provenance, limits, and checkpoint invalidation.
  • Profile experiments: model comparisons and source-grounded review.
  • Generated-stage cache and stage dependencies: reuse and invalidation mechanisms.
  • Generated-cache tests, dependency tests, and translation tests: targeted behavior checks.
  • CLI accounting tests and installed-package checks: fresh metadata and delivery boundaries.
  • Offline comparison snapshot: baseline, stage-call sequences, runtimes, and explicit limitations. The one-off probe is not a permanent benchmark command.
